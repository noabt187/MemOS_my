二、两个"坏节点"（毒化检索窗口）

2026-08-13 11:33:33（北京）写入，来自"分析睡眠状况"对话回写。 写入端 neo4j.py:_sanitize_neo4j_metadata 把嵌套 dict 用 json.dumps 字符串化，读端没有还原。

为什么"每条都搜不到"？ 默认 dedup=mmr 把 top_k 放大到 15，候选窗口必然覆盖这两个节点—— 只要它们进入候选集，整次检索的反序列化就抛异常 → 全部为空。 搜索睡眠类内容时尤其必现（坏节点本身就是睡眠记忆，永远排在候选最前面）。

三、时间线：为什么"当场能检索，重启后不行"

时间均为北京时间（UTC+8）。数据来自 Neo4j 节点 created_at。

重启无关数据完整性：记忆写入即同步落库（Neo4j / Qdrant 命名卷）， 服务关闭（lifecycle.py）只做 scheduler 收尾，不做任何数据持久化。 重启前后数据完全一致——"当场能搜"是因为当时坏节点还没写入，与"是否完全入库"无关。

六、修复方案

清掉 / 还原两个节点的字符串 internal_info，检索立即恢复，无需改代码。在 Neo4j Browser（http://localhost:7474，neo4j / 12345678）执行：

MATCH (n:Memory)
WHERE n.internal_info IS NOT NULL AND toString(n.internal_info) STARTS WITH '{'
SET n.internal_info = null
RETURN n.id, n.memory_type

两个目标节点：688b4c53-3fd4-42ad-a963-9bfb6da46210、8a433b4f-9c44-45a7-9de2-cc6346131016。

  • 读端还原（推荐）：构造 TextualMemoryItem 前把 internal_info 反解析回 dict——参考 dream/contextualization.py 已有的 _coerce_json_dict；可同时覆盖 postgres.embedding 的字符串问题。
  • 写端止损：src/memos/graph_dbs/neo4j.py:_sanitize_neo4j_value 不再把嵌套 dict 用 json.dumps 字符串化（Neo4j 原生支持 map 属性）。
  • 可观测性：single_cube.py:_search_text 的裸 except Exception: return [] 应记录异常（logger.exception），避免下次再静默吞错。
# 读端还原 internal_info 的参考模式（_coerce_json_dict 位于 dream/contextualization.py）
import json, ast

def _coerce_json_dict(value):
    if isinstance(value, dict):
        return value
    if isinstance(value, str):
        try:
            parsed = json.loads(value)
        except (ValueError, TypeError):
            try:
                parsed = ast.literal_eval(value)
            except (ValueError, SyntaxError):
                return None
        return parsed if isinstance(parsed, dict) else None
    return None

七、结论

  • ✅ 数据未丢失：23 条记忆 + 34 条向量完好（本页所有数字均为实测）。
  • ✅ 写入链路正常：add → 抽取 → 嵌入 → Neo4j+Qdrant 双写，实测 34→35 立即生效。
  • ❌ 检索链路被 2 个坏节点毒化：internal_info 字符串化 → 默认 dedup=mmr 放大 top_k 必然命中 → Pydantic 校验失败 → 异常被吞 → 空结果。
  • 🔧 恢复方式：执行上面 Cypher 清掉坏字段即可立即恢复；长期建议代码修复 + 不再静默吞异常。
